# Idempotency System Specification (NestJS)

Version: **v1**

---

# 1. Goal

Provide **server-side idempotency** for APIs that mutate resources.

This mechanism is designed to solve:

- Network retry
- HTTP timeout retry
- Duplicate requests caused by unstable connections
- UI accidental double submission (when the same Idempotency-Key is reused)

This mechanism **does not** solve:

- Malicious repeated requests with different keys
- Concurrent modification (Optimistic Lock should handle this)
- Rate limiting

---

# 2. Scope

Only enabled on APIs explicitly marked with

```ts
@Idempotent()
```

Not all PUT/PATCH/POST requests are automatically idempotent.

Reason:

- Some POSTs should create multiple resources.
- Some PATCHs don't require replay.
- Server should decide which APIs support idempotency.

---

# 3. Header

Request Header

```http
Idempotency-Key: <UUID v4>
```

Requirements

- UUID string
- Generated by client
- Must remain unchanged during retries
- Server never generates or modifies it

---

# 4. Frontend Specification

## 4.1 Automatic Injection

Lowest networking layer (fetch monkey patch / axios interceptor)

Pseudo code

```ts
if (needIdempotency(method) && !headers.has('Idempotency-Key')) {
  headers.set('Idempotency-Key', crypto.randomUUID());
}
```

Rules

- Existing header MUST NOT be overwritten.
- UI is allowed to manually provide the key.
- Retry must reuse the same request (thus the same header).

---

## 4.2 Supported Methods

Automatically inject for

- PATCH
- PUT

Optional

- POST
- DELETE

Never

- GET
- HEAD
- OPTIONS

# 9. Request Hash

Purpose

Validate whether the same key is reused for another request.

It is **NOT** the Redis key.

Algorithm

```
SHA256(

method +

normalizedPath +

canonicalJson(body)

)
```

Do NOT hash

- Authorization
- Date
- User-Agent
- Accept
- Accept-Language
- Host

Only hash business-related information.

If specific headers affect business logic

Example

```
X-Shop-ID
```

Those headers may be added using a whitelist.

# 11. Guard Responsibilities

Guard is responsible for

- Determine whether endpoint enables idempotency
- Read metadata
- Read header
- Compute request hash
- Acquire Redis lock
- Determine replay or conflict
- Store context on Request

Guard is NOT responsible for

- Replay response
- Write completed result
- Response formatting

---

# 12. Guard Flow

```
Receive Request

↓

GET Metadata

↓

Not @Idempotent

↓

return true

------------------

@Idempotent

↓

Read Idempotency-Key

↓

Missing Header

↓

return true
(or reject depending on policy)

↓

Compute request hash

↓

Redis Lookup
```

---

## Case A

Redis does not exist

```
SET key processing NX EX ttl
```

Success

```
req.idempotency = {

    replay: false,

    key,

    requestHash,

    ttl,

}
```

Return

```
true
```

---

## Case B

Redis status = processing

Return

```
409 Conflict
```

---

## Case C

Redis status = completed

Compare hash

Same

```
req.idempotency = {

    replay: true,

    record,

}
```

Return

```
true
```

---

## Case D

Completed

Hash mismatch

```
409 Conflict
```

Reason

Client reused Idempotency-Key incorrectly.

# 14. Interceptor Responsibilities

Interceptor is responsible for

- Replay cached response
- Save successful response
- Remove processing lock on failure
- Optionally replay errors

Interceptor does NOT

- Decide whether endpoint supports idempotency
- Compute metadata

---

```

```

```

↓

```

```

```


Delete Redis key

```

```

```

```

# 20. Limitations

This mechanism only guarantees

```
Same Idempotency-Key

+

Same Request

↓

Same Result
```

It does **not** guarantee

- Protection against different keys
- Business-level deduplication
- Concurrent editing
- Rate limiting

Those concerns should be handled by

- Rate Limiter
- Authentication
- Authorization
- Optimistic Lock (version / ETag / updatedAt)
- Business validation

---

# 21. Future Extensions

Possible future enhancements

- Configurable TTL per endpoint
- Replay only specific HTTP status codes
- Redis Cluster support
- Response compression before caching
- Cached response size limit
- Automatic cleanup metrics
- Monitoring (hit rate, replay count, conflict count)
- Pluggable storage backend (Redis, Memory, Database)
- Configurable hash whitelist for business-critical headers
